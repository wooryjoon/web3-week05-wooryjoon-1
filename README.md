## 1. EOA와 ERC-4337: "열쇠"에서 "스마트 도어락"으로

### EOA(Externally Owned Account)의 한계
우리가 흔히 사용하는 메타마스크 지갑이 바로 **EOA**입니다. 이는 개인키 하나가 모든 권한을 독점하는 구조입니다.

* **리스크:** 개인키를 분실하면 자산을 영영 찾을 수 없디. 반대로 유출되면 즉시 모든 자산을 도난당한다. "내 돈은 내가 지킨다"는 철학은 멋지지만, 그 책임은 무겁다.
* **불편함:** 트랜잭션을 발생시킬 때마다 가스비(수수료)를 지불해야 하며, 매번 복잡한 서명을 거쳐야 한다. 웹2의 간편한 로그인에 익숙한 사용자에게는 거대한 진입장벽이 될 수 있따.

### ERC-4337, 계정 추상화의 등장
**ERC-4337**은 지갑을 단순한 '주소'가 아닌 **'스마트 컨트랙트'**로 만드는 기술.

| 비교 항목 | EOA (기존 지갑) | ERC-4337 (스마트 지갑) |
| :--- | :--- | :--- |
| **제어 주체** | 개인키 소유자 (1인) | 스마트 컨트랙트 로직 (다양함) |
| **복구 방식** | 시드 구문 분실 시 복구 불가 | 사회적 복구(친구 도움), 이메일 등 가능 |
| **수수료 지불** | 반드시 본인이 해당 코인으로 지불 | **Paymaster**를 통해 대납 혹은 타 코인 지불 가능 |
| **일괄 처리** | 여러 작업 시 매번 서명 필요 | 여러 작업을 한 번에 묶어서 처리(Batch) 가능 |

## 2. 좋아진 사용성, 그 뒤에 숨은 운영의 고민

사용자가 편해지는 만큼, 시스템을 관리하는 측면에서는 새로운 문제에 직면하게 된디.

1.  **승인 규칙(Rule):** "하루 100만 원 이상은 다중 서명 필요", "특정 주소로만 송금 가능" 같은 로직을 컨트랙트에 심어야 합니다. 이 로직의 취약점이 곧 보안 사고로 이어집니다.
2.  **복구 권한:** 사용자가 키를 잃었을 때 누가 복구를 도와줄 것인가? 중앙화된 관리자가 개입하면 블록체인의 탈중앙화 가치와 충돌할 수 있습니다.
3.  **장애 시 책임:** 스마트 컨트랙트 코드 자체의 버그로 자산이 묶인다면, 지갑 서비스 제공자가 어디까지 책임을 져야 할지가 법률적·운영적 쟁점입니다.

### 은행 시스템과의 비교
은행의 방식과 비교하면 블록체인의 변화 방향이 뚜렷해진다.

* **공통점:** "사용자 인증 - 권한 확인 - 거래 승인"의 단계를 거친다는 논리 구조는 비슷합니다. ERC-4337을 통해 블록체인도 은행처럼 **'비밀번호 찾기'**나 **'이용 한도 설정'**이 가능해지고 있습니다.
* **차이점:** 은행은 데이터베이스(DB)를 직접 수정하여 거래를 확정하지만, 블록체인은 여전히 모든 기록이 온체인에 남으며 위변조가 불가능합니다. 은행은 '신뢰의 주체'가 기관이지만, 블록체인은 '신뢰의 주체'가 코드(Code)입니다.

## 3. 블록체인 트릴레마와 L2의 해법

### 트릴레마(Trilemma)란 무엇인가?
블록체인은 **탈중앙화, 보안성, 확장성** 세 가지를 동시에 만족시키기 어렵다는 고질적인 문제를 안고 있다.. 
* 모두가 검증하면 안전하지만 느려지고(확장성 부족)
* 소수만 검증하면 빠르지만 보안이나 탈중앙화 자체에 대한 위협이 될 수 있음.

### L2(Layer 2)가 구원투수로 등장한 이유
확장성 문제를 해결하기 위해, 모든 거래를 메인 블록체인(L1, 예: 이더리움)에서 처리하지 않고 **별도의 층(L2)**에서 처리한 뒤 결과만 L1에 기록하는 방식이 등장.

> **쉽게 비유하자면:** > 모든 영수증을 본사(L1)에서 일일이 검사하면 병목 현상이 발생하므로, 지점(L2)에서 장부를 묶어 정산한 뒤 최종 요약본만 본사에 보고하는 것과 같다. 이를 통해 수수료는 낮추고 속도는 획기적으로 높일 수 있음.
 (그렇지만, L2에서 이루어진 거래에 대한 해킹이 이루어진 채로 L1 장부에 거래가 올라가게 된다면? 이에 대한 해법은 무엇일까)

## 4. 결론: 금융회사 IT 관점에서의 현실적 대안

은행 IT 관점에서 가장 현실적으로 받아들일 수 있는 구조는 **"커스터디(수탁) 기반의 하이브리드 계정 추상화 모델"

1.  **인프라 레이어:** 보안성과 검증이 완료된 **이더리움 L2(Optimism, Arbitrum 등)**를 활용하여 처리 속도와 비용 문제를 해결.
2.  **지갑 구조:** 사용자는 편리하게 지갑을 사용하되(ERC-4337), 개인키의 일부 혹은 복구 권한을 금융기관이 안전하게 관리(MPC 기술 등 활용)하는 형태. 
3.  **운영 전략:** 가스비는 금융사가 포인트나 이벤트로 대납(Paymaster 활용)해주어 사용자 경험을 웹2 수준으로 끌어올리는 것이 핵심.

결국, 사용자는 자기가 블록체인을 쓰는지도 모를 만큼 매끄러운 UX를 제공하면서, 뒷단(Backend)에서는 블록체인의 투명성과 보안성을 챙기는 구조가 금융권 Web3 서비스의 승부처가 될 것이라고 생각한다.
